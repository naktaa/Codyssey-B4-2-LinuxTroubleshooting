## Major

### Major-1: 관측 종료 경계에서 앱 상태와 결과 문구가 어긋날 수 있음

- 위치: `observe-memory.sh` (삭제 전) 74~85행, 86~118행, 120~136행 (`natural_exit` 최종 판정·관제 회수·결과 기록).
- 확인 사실: `natural_exit`와 `state`는 관제 프로세스의 `wait` **전**에 마지막으로 결정됩니다. 이후 관제가 끝나고 결과 파일과 화면 문구를 쓸 때 앱 상태를 다시 읽거나 CSV의 `EXITED` 행과 대조하지 않습니다.
- 발생 조건·영향: 시간 제한 직전 마지막 `ps`에서는 앱이 살아 있었으나 그 직후 앱이 자연 종료하면, 관제가 `EXITED`를 기록하고 정상 종료하더라도 결과는 “app still present”와 생존 하한으로 기록될 수 있습니다. 관제에 TERM을 보낸 뒤 앱이 종료해도 같은 결과가 가능합니다. 이 경우 CSV·PID/포트 출력과 요약의 생존 상태가 충돌하여 TASK의 자연 종료/시간 만료 구분과 증거 해석을 흐립니다. 이는 정적 코드 경로에서 추론한 경합 위험이며 실제 재현은 확인하지 않았습니다.
- 최소 수정 방향: 관제 회수 뒤 앱 상태를 다시 확인하고, `EXITED` 표본 및 종료 시점과 일관되게 최종 상태·문구를 정하십시오. 관측 창 뒤 종료처럼 구분할 수 없는 경계는 종료 시점 미확정으로 표현하면 됩니다. 앱 종료 신호는 추가하지 않아야 합니다.

## Minor

- 위치: `observe-memory.sh` (삭제 전) 111~124행 (`outcome` 선택과 마지막 `printf`·`tail`).
- 확인 사실: 성공 결과 문구를 포함한 `printf`와 마지막 앱 로그 `tail`을 한 조건으로 실행합니다. 앞의 `printf`가 성공하고 뒤의 `tail` 또는 쓰기가 실패하면 종료 코드는 1로 바뀌지만 이미 기록된 `Outcome`은 성공 문구 그대로 남을 수 있습니다.
- 발생 조건·영향: 앱 로그 읽기 실패 또는 요약 파일 쓰기 실패 때 부분 증거의 `Outcome`만 읽으면 완료로 오해할 수 있습니다. 화면의 오류와 종료 코드는 실패를 알리므로 영향은 제한적입니다. 실제 파일 실패는 재현하지 않았습니다.
- 최소 수정 방향: 최종 기록 오류가 확인되면 결과 문구도 불완전 상태로 남기거나, 성공 판정 전에 필요한 읽기·쓰기 결과를 확정하십시오.
