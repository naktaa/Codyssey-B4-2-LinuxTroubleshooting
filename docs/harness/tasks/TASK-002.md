# TASK-002: 메모리 설정 전후 비교 및 OOM 보고서

## Goal

기존 실행·관제 도구로 MEMORY_LIMIT 변경 전후 메모리 증가와 생존 시간을 비교하고, 실제 증거에 근거한 MemoryGuard 종료 보고서 1건을 작성한다.

## Context

- [TASK-001](TASK-001.md)의 실행·CSV 관제 도구, 독립 리뷰, 사용자 검증은 완료했다. TASK-001 학습 이해 완료는 별도로 미확인이다.
- 이전 사용자 실행에서 MEMORY_LIMIT=256의 MemoryGuard 자체 종료와 동일 PID의 CSV EXITED를 확인했다. 설정 변경 전후 비교는 아직 수행하지 않았다. 근거는 [WORKLOG](../WORKLOG.md)를 따른다.
- 환경: macOS 호스트의 OrbStack Linux 머신, 일반 사용자, Bash, Docker 미사용.
- 난이도: MEDIUM. 추천 모델: GPT-6 Sol. Reasoning: Medium.
- 추천 이유: 기존 도구를 활용하되 실행 조건·시각·지표·종료 원인을 연결하고 관측 사실과 추론을 구분해야 한다.
- Review 예상: RECOMMENDED — 평가 산출물의 증거 연결·해석 검토. 실제 변경 위험을 보고 PM이 재판정한다.
- Review Decision: 구현 인계 전이므로 미판정.
- Step 승인: 2026-09-30 사용자의 “다음 작업 진행. 뭘 구현할건지 자세히 설명도 해줘” 요청으로 앞서 제안한 메모리 비교·보고서·학습 보완 범위 진행 승인.
- 구현 계획 승인: 미승인. Implementer가 수정 파일·방향·영향을 제시하고 승인을 받은 뒤 작성한다.
- 변경 기준점: `48438ce11b3e8c311b142d670515a50ac1f55e1a`. TASK 작성 전 작업 트리는 clean이었다.

## Requirements

- [MISSION §2·§4](../MISSION.md), [REQ-002](../REQUIREMENTS.md): 물리 메모리 증가 관측, MemoryGuard 임계치 초과·자체 종료 로그, MEMORY_LIMIT 변경 전후 최소 2회 실행 및 생존 시간 비교.

## Constraints

- Linux 일반 사용자 및 미션의 필수 환경변수·경로·포트 조건을 유지한다. MEMORY_LIMIT은 정수 50~512 MB 범위다.
- 제공 바이너리 수정·디컴파일·리버스 엔지니어링은 금지한다. Linux 표준 도구와 기존 스크립트를 활용한다.
- 실제 실행·테스트는 사용자 담당이다. AI는 명령 안내·정적 확인·사용자가 제공한 증거 분석을 담당한다.
- 원본 로그·CSV를 덮어쓰거나 삭제하지 않는다. 실제 credential은 문서에 포함하지 않는다.
- 한 비교에서는 MEMORY_LIMIT만 바꾸고 CPU_MAX_OCCUPY·MULTI_THREAD_ENABLE 등 나머지 조건을 동일하게 유지하며 값을 기록한다.
- 다른 장애가 먼저 발생하면 실패·관측 한계를 기록한다. 예상 결과에 맞춰 원인이나 생존 시간을 만들어내지 않는다.
- 전역 셸 설정, 패키지·프레임워크 추가, 자동 실행·재시작·종료·정리 도구는 도입하지 않는다.

## Scope

- 기존 도구로 두 설정을 순차 실행하는 수동 실험 안내: 설정 확인, 실행·관제, 실행별 경로·PID 기록, 부트·종료 로그 확인, 다음 실행 전 실제 프로세스·포트 상태 확인.
- 256MB와 512MB를 비교 후보로 제안한다. 구체적인 실행 명령과 측정 기준은 Implementer가 설명하고 계획에 포함한다.
- 실행별 설정, 시작·종료 시각, 생존 시간과 계산 기준, RSS 추이·관측 최대값, MemoryGuard 종료 근거를 비교한다. 이전 증거를 재사용하려면 조건·원본 존재·대상 연결을 확인한다.
- OOM 보고서 초안을 준비하고 사용자 실제 결과를 받은 뒤 증거·분석·비교를 채운다. 미수집 부분은 미검증으로 표시한다.
- runs/는 Git 제외이므로 보고서에 핵심 CSV 행·앱 로그·명령 출력을 출처와 함께 발췌해 저장소만으로 근거를 읽을 수 있게 한다.
- README에 실험 안내와 보고서 연결을 추가하고, 단일 학습 노트의 TASK-002 절을 작성한다.

## Out of Scope

- CPU·Deadlock 본 실험 및 해당 보고서, 스케줄링 보너스.
- 기존 실행·관제 스크립트의 기능 변경, 자동 분석기·그래프 생성기 개발. 필요성이 발견되면 별도 변경 계획을 제시한다.
- 실제 GitHub Issue 게시, PDF 제출, commit/push.
- MEMORY_LIMIT 상향을 메모리 누수의 근본 해결로 표현하는 것.

## Implementation Notes

prepare-env.sh는 현재 셸의 MEMORY_LIMIT을 읽고 허용 범위를 확인해 앱에 export한다. 실행마다 새 로그 디렉터리를 생성하고 부모·자식 PID를 구분한다. monitor.sh는 RSS(KiB), 시스템 대비 %MEM, 프로세스 수명 평균 CPU를 기록한다.

관제 시작과 프로세스 시작은 같지 않다. EXITED 관측 시각도 실제 종료 순간과 차이가 있으므로 비교에 사용하는 시작·종료 기준을 두 실행에 동일하게 적용한다. 마지막 RSS 표본이 실제 종료 순간의 최대 메모리라고 단정하지 않는다. 더 높은 한계에서 CPU 보호 조치 등이 먼저 발생할 가능성은 실제 로그로 판단한다.
