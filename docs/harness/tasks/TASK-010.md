# TASK-010: 앱 로그 근거의 간단한 터미널 장애 경고

## Goal

[monitor.sh](../../../monitor.sh)의 기존 앱 로그 검사와 관측 종료 흐름을 재사용하여, 확인된 임계치 신호·락 대기 신호를 유형별 `[WARNING]`으로 간결하게 알린다.

## Context and Approval

- 사용자 요청: 현재 monitor.sh에 경고를 추가하고 README에 조건만 짧게 설명. “검토하지 말고 바로 수정 시작”을 명시했으므로 구체적으로 지정된 범위에서 바로 구현하고 독립 리뷰를 생략한다.
- 새 기능이므로 문서 정리 TASK-009와 분리한다. PM은 기능 source를 직접 수정하지 않고 별도 Implementer에게 맡긴다.
- 난이도: LOW. 기존 로그 검사 결과의 터미널 표시만 추가한다. Implementer 지정 설정은 [모델 정책](../MODEL_POLICY.md)에 따라 `gpt-6-sol` / `medium` / `fork_turns="none"`이다. TASK-009의 일회성 모델 예외를 새 TASK에 자동 적용하지 않는다.
- 기존 monitor.sh와 README 모두 선행 사용자 변경이 있으므로 수정 직전 사본을 기준으로 이번 차이만 대조한다. 원문 로그·관측 결과·기존 코드 변경은 보존한다.

## Execution State

- 현재 단계: 사용자 검증 대기.
- 승인 근거: 사용자가 수정 파일·재사용 함수·세 감지 대상·출력 내용·시점·유지할 동작·제외 범위를 직접 지정하고 즉시 수정을 지시했다. 별도 계획 승인·리뷰 대기로 멈추지 않는다.
- Review 예상: SKIP — 독립 검토를 생략하라는 사용자 지시. Implementer의 필수 정적 self-check와 미실행 범위 표시는 유지한다.
- 다음 행동: Implementer가 두 파일만 최소 수정하고 변경 위치·기존 동작 영향·정적 검증 결과를 PM에 반환한다.
- 수정 직전 기준: `/tmp/task010-warning-d7wcnr8c`의 두 파일 사본과 기존 추적 파일 SHA-256 목록. 현재 두 파일의 선행 사용자 변경을 포함한 내용을 기준으로 대조한다.
- 구현 완료: `show_log_signal()`에 선택적 경고 설명 인자를 추가했다. 기존 요약 쓰기가 성공한 로그 일치 분기에서만 유형·이유·같은 대표 근거 줄을 터미널에 표시한다. MemoryGuard 한도 초과·앱 CPU 임계치·WAITING/BLOCKED 세 호출에만 인자를 전달하고 자기 종료·Watchdog 호출은 유지했다. README는 3/4인자 관측 종료 시점의 조건과 Deadlock 의심임을 짧게 설명한다.
- 동작 영향의 정적 확인: grep 미일치·읽기 실패의 기존 처리를 유지했다. summary 쓰기 실패는 `return 1`로 보존하고, 경고 출력 실패는 기존 수집 결과를 변경하지 않도록 처리했다. CSV·관제 루프·trap/wait·PID 식별/정리·실행 인자·2인자 경로는 수정하지 않았다. 수정 직전 사본 대비 추적 파일 변경은 monitor.sh와 README뿐이었다.
- 문법 확인: CRLF를 제거한 표준입력에 `bash -n` 정적 검사를 수행해 통과했다. 실제 CRLF 파일·앱 실행 또는 fixture 테스트 성공으로 기록하지 않는다. 파일의 기존 UTF-8/CRLF는 보존했고 다른 실행 결과·원문은 수정하지 않았다.
- Review Decision: SKIP — 사용자의 명시적 독립 검토 생략 지시를 따랐으며 제한된 로그 표시 추가다. 별도 Reviewer·리뷰 문서는 만들지 않았다. 요청한 `gpt-6-sol` / `medium` 호출이 수락되고 결과를 회수했으며 실제 실행 모델 메타데이터는 별도 확인하지 않았다.
- 다음 행동: 사용자가 기존 설정값 명령으로 실제 경고·근거 줄, observation.txt/CSV 기록과 정리 결과를 확인한다. 실행 검증 후 최종 학습 정리로 마감한다. 구현과 실행 검증을 구분한다.

## Requirements

- [MISSION](../MISSION.md) §2·§4의 OOM/CPU/Deadlock 증거 해석을 보조한다. 경고는 사용자 추가 요청이며 원문의 새 필수 요구로 확대하지 않는다.
- MemoryGuard 한도 초과와 CPU 임계치 위반은 해당 앱 로그가 발견된 경우에만 알린다. CPU는 앱 내부 Load 임계치이며 OS CPU 과점유로 단정하지 않는다.
- WAITING/BLOCKED 등 실제 스레드 자원 대기 로그는 Deadlock **의심**으로 표시한다. 로그 한 줄만으로 순환 교착을 확정하거나 실제 CPU/MEM 정체를 측정했다고 주장하지 않는다.
- 각 경고는 유형·원인/의심 이유·대표 근거 로그를 짧게 포함한다. 일치 없음·로그 읽기 실패를 장애 발생으로 출력하지 않는다.

## Scope and Boundaries

- 수정: [monitor.sh](../../../monitor.sh)의 `show_log_signal()` 및 기존 앱 로그 검사 호출부, [README](../../../README.md)의 짧은 경고 조건 설명.
- 기본 방향: 기존 성공한 로그 검사 결과를 재사용하고 종료 전 요약 시점에 유형별 경고를 한 번 표시한다. 실시간 감시 루프나 별도 알림 구조는 만들지 않는다.
- 유지: 기존 CSV와 observation.txt 형식·내용, 앱 로그 읽기 실패 처리, 반환값, PID 식별·정리, trap·wait·컴파일·실행 인자와 2인자 PID/CSV 경로.
- 제외: 새 종료/Watchdog/SELF-TERMINATED 경고, 종료 이벤트 알림, 자동 장애 판정·추가 kill, 이메일·웹훅·의존성·별도 서비스·새 실험·바이너리 실행·Git 쓰기.
- 새 터미널 출력 실패가 기존 summary 쓰기 실패를 숨기거나 기존 정리 흐름을 건너뛰지 않도록 한다.

## Acceptance Criteria

- [ ] 세 신호가 실제 로그에 있을 때만 해당 유형의 `[WARNING]`과 근거가 표시된다.
- [ ] 앱 내부 CPU 임계치와 OS CPU, Deadlock 의심과 확정 진단을 구분한다.
- [x] 종료 로그·단순 프로세스 종료·도구 정리만으로 새 장애 경고를 만들지 않는다(수정 범위 정적 확인).
- [x] 기존 기록·반환값·PID 정리·인자 분기는 유지되고 변경이 경고 표시 범위를 넘지 않는다(소스 대조, 실행 미검증).
- [x] README에 감지 조건과 출력 시점을 짧게 설명한다.
- [x] 정적 문법·변경 범위를 확인하고 실제 실행 미검증을 구분한다. 앱 실행·실제 테스트는 기존 사용자 담당 규칙을 따른다.

## 사용자 실행 확인 안내

기존 안전한 실험 환경에서 각 실행의 정리 결과를 확인한 뒤 다음 명령을 실행한다. 아래는 사용자 실행 안내이며 AI는 실행하지 않았다.

```bash
bash ./monitor.sh 128 80 false 60
bash ./monitor.sh 512 80 false 60
bash ./monitor.sh 512 40 true 60
```

- 실제 앱 로그에 해당 신호가 있으면 관측 종료 시 유형별 `[WARNING]`과 `Evidence:` 줄을 확인한다. 설정만으로 경고 발생을 보장하지 않는다.
- 일치 로그가 없으면 해당 경고가 없어야 한다. CPU 경고는 앱 내부 Load이고 Deadlock 경고는 의심으로 표시되는지 확인한다.
- 기존 CSV·observation.txt·정리/포트 결과와 기존 2인자 경로는 별도로 사용자 확인한다. 실제 결과를 받기 전 통과로 기록하지 않는다.
