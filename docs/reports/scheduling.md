# [Analysis] 정상 실행 로그의 스케줄링 패턴 추론

## 1. Description (관찰 개요)

`Healthy System Monitoring` 한 실행에서 앱은 A·B·C를 등록 순서대로 완료. 완료 전 다른 작업의 진행 로그 없음. 이는 앱 로그 패턴이며 OS의 실제 CPU 점유 순서나 스케줄링 정책 측정은 아님.

## 2. Evidence & Logs (증거 자료)

아래는 같은 실행의 등록·시작·완료 기록 8행. 전체 진행률 로그와 206/216/206ms·52/51ms 기록 간격은 [학습 절](../study-note.md#정상-실행의-전체-진행-로그-보존)에 보존.

## 3. Root Cause Analysis (패턴 분석)

| 후보 | 일반 처리 기준 | 관찰과 구별 한계 |
| --- | --- | --- |
| FCFS | 먼저 도착한 작업부터 완료까지 처리 | A→B→C 순차 완료와 맞음. 실제 도착·선택 시각이 없어 확정 불가. |
| SJF | 예상 실행 시간이 가장 짧은 작업부터 완료까지 처리 | 예상 실행 시간·선택 당시 대기 작업이 없어 같은 순서였는지 판단 불가. |
| SRT | 예상 남은 시간이 가장 짧은 작업 우선, 필요 시 선점 | 남은 시간 추정값·새 작업 도착 시각이 없어 선점·선택 기준 판단 불가. |
| RR | 실행 가능한 작업에 시간 할당량씩 차례로 실행 기회 제공 | 교차 진행은 기록되지 않음. 긴 할당량이나 기록 밖 교체라면 배제 불가. |
| Priority | 우선순위가 높은 작업부터 처리 | 우선순위 값이 없어 A→B→C가 우선순위 결과인지 구별 불가. |
| HRN | 대기 시간·예상 실행 시간으로 계산한 응답률이 높은 작업부터 처리 | 도착·대기·예상 실행 시간이 없어 응답률·선택 기준 판단 불가. |

FCFS형은 관찰 가설임. 여섯 후보의 실제 적용 여부·순위는 확정 불가. 로그 간격은 CPU 실행 시간·RR 시간 할당량이 아니며 `Thread-A/B/C`도 OS TID가 아님. 상세 구별 조건은 [학습 절](../study-note.md#후보를-구별할-수-있는-근거와-없는-근거)에 보존.

## 4. Workaround & Verification (조치·검증 범위)

설정 변경·코드 조치·추가 실험은 하지 않았음. 실제 정책 검증에는 작업 도착·선택 시각, 우선순위, OS 스레드 실행 기록이 필요함.

아래는 일반 알고리즘의 장단점·서비스 적합성 분석이며 실제 앱 성능 측정 결과는 아님.

| 알고리즘 | 장점 | 단점 | 적합한 서비스·작업 |
| --- | --- | --- | --- |
| FCFS | 접수 순서 예측, 강제 교체 부담 적음 | 긴 작업 뒤 짧은 요청도 지연 | 순서 중심 배치. 빠른 응답이 중요한 웹에는 불리 |
| SJF | 짧은 작업의 대기 감소 | 실행 시간 예측 필요, 긴 작업 기아 가능 | 실행 시간 추정이 가능한 배치 |
| SRT | 새로 온 짧은 작업에 빠른 기회 제공 | 남은 시간 예측·선점 부담, 긴 작업 기아 가능 | 짧은 요청이 수시 도착하는 처리 작업 |
| RR | 실행 기회 분배, 대화형 응답에 유리 | 짧은 할당량은 전환 부담, 긴 할당량은 응답 지연 | 시분할·대화형 서비스 |
| Priority | 중요한 작업 우선 처리 | 낮은 우선순위 기아 가능 | 중요도가 구분된 작업·서비스 |
| HRN | 대기 시간을 반영해 긴 작업의 불이익 완화 | 실행 시간 추정 필요, 비선점으로 긴 작업 중 응답 지연 | 대기 시간도 고려하는 비선점 배치 |
