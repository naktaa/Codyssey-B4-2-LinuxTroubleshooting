# Linux 장애 분석 학습 노트

이 파일에는 TASK가 진행될 때마다 학습 내용을 이어서 작성합니다. 코드가 바뀌면 해당 절을 갱신합니다. 실제 사용자 실행 결과와 설명용 예시를 구분하며, 문서 작성이 사용자 이해 완료를 뜻하지는 않습니다.

## 전체 미션 목표와 읽기 순서

기준은 [MISSION](harness/MISSION.md)과 [REQUIREMENTS](harness/REQUIREMENTS.md)입니다. 최종 산출물은 OOM·CPU·Deadlock 보고서 3건이며, 각 보고서에서 현상 → 증거 → 원인 → 조치 및 전후 비교를 설명해야 합니다.

1. [TASK-001: 실행 환경과 관제](#task-001-linux-실행-환경-및-관제-준비): 셸·프로세스·환경변수 → 앱 시작과 PID → CSV 수집 → 종료와 오류 → 실제 증거 읽기 순서로 공부합니다.
2. 메모리 분석(예정): 메모리 구조·누수의 영향, MemoryGuard와 OS의 메모리 부족 처리 구분, MEMORY_LIMIT 전후 비교.
3. CPU 분석(예정): 프로세스 CPU 과점유와 시스템 지연, 측정 구간, Watchdog와 CPU_MAX_OCCUPY 비교.
4. Deadlock 분석(예정): 살아 있지만 진행하지 못하는 상태, 스레드·락·순환 대기, MULTI_THREAD_ENABLE 비교.
5. 보고서 정리(예정): 육하원칙, 로그와 관제 수치의 연결, 임시 조치와 근본 해결의 구분. 스케줄링 추론은 선택 보너스입니다.

공통 제약은 Linux 일반 사용자 실행, 지정된 환경변수·경로·포트 준수, 표준 도구 활용, 바이너리 디컴파일·역공학 금지입니다. Docker는 필수가 아니며 현재는 macOS 호스트의 OrbStack Linux 머신을 사용합니다.

소스 링크는 이 Markdown 파일 기준의 상대 경로와 `#L시작행`을 사용합니다. 행 범위가 표시된 링크도 해당 범위의 시작 행으로 연결합니다. GitHub 코드 뷰의 줄 앵커 형식이며, 로컬 Markdown 뷰어의 줄 이동 지원은 환경에 따라 다를 수 있습니다. 코드 변경 후 링크의 행 번호도 갱신해야 합니다.

## TASK-001: Linux 실행 환경 및 관제 준비

### 미션에서 이번 단계의 위치

첫 단계에서는 장애를 고치는 대신 장애를 관찰할 준비를 했습니다. 제공 바이너리는 분석 대상이고, 직접 만든 셸 스크립트는 실행 조건과 증거 수집을 돕습니다. 관측할 PID나 로그가 잘못되면 이후 원인 분석도 잘못되므로, 실행별 로그 분리와 실제 작업 프로세스 식별이 먼저 필요합니다.

관련 자료: [TASK-001](harness/tasks/TASK-001.md), [사용 방법](../README.md), [독립 리뷰](harness/reviews/REVIEW-TASK-001.md), [실제 검증 기록](harness/WORKLOG.md).

### 먼저 이해할 개념

**터미널·셸·프로세스:** 터미널은 입력과 출력을 보여 주고, Bash 셸이 명령을 해석합니다. 바이너리를 실행하면 프로세스가 생깁니다. 입력 프롬프트가 보인다고 백그라운드 앱까지 종료된 것은 아닙니다.

**PID와 PPID:** PID는 프로세스 번호, PPID는 부모 프로세스 번호입니다. 제공 실행 파일은 별도의 작업 자식을 생성하는 것으로 관찰됐습니다. 이번 관제는 그 자식을 대상으로 합니다. 시간이 지나면 PID가 재사용될 수 있어 숫자만 장기간 보관하지 않고 실행 디렉터리와 함께 해석합니다.

**셸 변수와 환경변수:** `run_dir`은 현재 셸이 다음 명령에서 참조하는 값입니다. `export MEMORY_LIMIT=256`처럼 내보낸 변수는 이후 실행하는 자식 프로그램이 물려받습니다. 자식에서 값을 바꾼다고 부모 셸 값이 자동 변경되지는 않습니다.

**source와 bash 실행:** `source ./prepare-env.sh`는 현재 셸에서 파일을 읽으므로 PID와 경로가 뒤의 명령에도 남습니다. `bash ./monitor.sh ...`는 별도 Bash에서 관제를 실행합니다. 따라서 monitor의 `set -u`, `set -C`, `LC_ALL=C`는 그 관제 프로세스 환경에 적용됩니다.

**종료 상태:** 관례상 반환값 0은 성공, 0이 아니면 실패입니다. `$?`는 바로 앞 명령의 종료 상태이므로 다른 명령을 실행하기 전에 읽어야 합니다. `A && B`는 A가 성공했을 때만 B를 실행합니다. 다음 줄에 별도로 쓴 C까지 조건부로 만드는 것은 아닙니다.

### 실행 흐름을 따라 코드 읽기

#### 1. 현재 셸에서 준비 함수를 호출한다

입력은 다음과 같습니다. 여기의 명령은 사용 흐름 설명이며 지금 다시 실행할 필요는 없습니다.

```bash
source ./prepare-env.sh && bash ./monitor.sh "$app_pid" "$run_dir/monitor.csv"
```

[prepare-env.sh 4~7행](../prepare-env.sh#L4)은 `BASH_SOURCE[0]`과 `$0`을 비교해 직접 실행을 거부합니다. `source`일 때는 함수 정의를 읽고 [157행](../prepare-env.sh#L157)에서 `codyssey_prepare_env`를 호출합니다. 함수가 0을 반환해야 `&&` 뒤의 관제가 시작됩니다. 큰따옴표는 경로에 공백이 있어도 하나의 인자로 전달되도록 합니다.

#### 2. 중복 실행과 환경 오류를 먼저 확인한다

[prepare-env.sh 14~58행](../prepare-env.sh#L14)의 `codyssey_prepare_env`은 필요한 도구, 기존 PID, OS, UID, 아키텍처, 실행 권한, 포트를 확인합니다. `command -v`는 명령 존재를, `ps -p`는 PID 존재를 확인합니다. `ss`는 15034번 포트의 수신 소켓을 조회합니다. 포트 검사는 이 순간의 상태일 뿐 실제 bind 성공까지 보장하지 않으므로 앱 부트 로그도 봐야 합니다.

`$(uname -m)`은 명령 출력을 변수에 담는 명령 치환입니다. `case`는 아키텍처에 맞는 바이너리를 고릅니다. macOS 호스트의 칩 이름 대신 실제 Linux 머신의 응답을 사용합니다. 확인 실패 시 `return 1`로 함수와 준비 절차를 중단하며, 현재 대화형 셸 자체를 종료하지 않습니다.

#### 3. 설정값을 검증하고 필요한 경로를 준비한다

[prepare-env.sh 60~102행](../prepare-env.sh#L60), `codyssey_prepare_env`.

```bash
selected_memory=${MEMORY_LIMIT:-256}
```

`${변수:-기본값}`은 변수가 없거나 비었을 때 기본값을 사용합니다. 예를 들어 설명용 입력 `MEMORY_LIMIT=49`는 문자열 모양 검사에는 맞지만 50~512 범위 검사에 실패합니다. `[[ ... =~ ... ]]`는 정규식 검사, `(( ... ))`는 정수 연산입니다. `10#`은 숫자를 10진수로 해석하도록 지정합니다. 코드가 값의 모양을 먼저 검사하므로 잘못된 문자열을 곧바로 산술식에 넣지 않습니다.

`local` 변수는 함수 내부 준비값이며, 검증된 값은 나중에 전역 변수와 환경변수로 전달합니다. `mkdir -p`는 필요한 디렉터리를 준비합니다. 기존 키가 있으면 `cmp`로 공개 시험용 값과 비교하고 덮어쓰지 않습니다. `-L` 검사로 심볼릭 링크가 있는 경우도 새 파일 생성 경로에서 제외합니다.

키를 만들 때 `(set -C; printf ... > "$key_file")`의 괄호는 서브셸입니다. 덮어쓰기 방지 옵션을 그 작은 작업에만 적용해 사용자의 현재 셸 옵션을 바꾸지 않습니다. 여기의 키는 미션에서 공개한 시험용 값이며 실제 서비스 인증정보와 구분해야 합니다.

#### 4. 새 로그 공간을 확보한 다음 앱을 시작한다

[prepare-env.sh 104~128행](../prepare-env.sh#L104), `codyssey_prepare_env`.

`mktemp -d`는 실행별 디렉터리를 생성합니다. 날짜만 사용하면 같은 초의 실행끼리 이름이 겹칠 수 있으므로 임의 접미사가 붙습니다. 앱 로그에 시작 시각을 기록한 다음 환경변수를 export하고 `run_dir`을 새 경로로 갱신합니다.

```bash
"$binary" >> "$run_dir/app.log" 2>&1 &
launcher_pid=$!
```

`>>`는 표준 출력(1)을 파일에 이어 씁니다. 그 뒤 `2>&1`은 표준 오류(2)도 같은 출력 대상으로 보냅니다. 마지막 `&`는 백그라운드 실행이고 `$!`는 방금 시작한 비동기 작업의 PID입니다. 셸은 앱 종료를 기다리지 않고 PID 확인 단계로 넘어갑니다. 앱의 로그와 준비 스크립트의 터미널 안내는 서로 다른 출력입니다.

#### 5. 부모가 만든 실제 작업 자식을 관제 대상으로 고른다

[prepare-env.sh 130~154행](../prepare-env.sh#L130)의 `codyssey_prepare_env`은 부모가 살아 있는지 확인하고 `ps --ppid`로 직접 자식을 찾습니다. 자식 하나만 식별될 때 정규식 캡처 `BASH_REMATCH[1]`을 `app_pid`에 넣습니다. 자식이 없으면 최대 다섯 번 조회하며 사이에 기다립니다. 여러 자식이 나오면 임의로 선택하지 않고 오류를 반환합니다.

예를 들어 실제 실행에서 부모는 12153, 작업 자식은 12158이었습니다. `$!`로 얻은 부모만 관제하면 우리가 찾는 메모리 증가를 놓칠 수 있습니다. `Started (boot unverified)`는 PID 식별 성공이지 앱 내부의 모든 부트 조건 통과 판정은 아닙니다.

#### 6. 관제 인자를 확인하고 새 CSV를 연다

[monitor.sh 3~39행](../monitor.sh#L3), 최상위 준비 단계.

입력은 대상 PID와 새 로그 경로 두 개입니다. `$#`는 인자 개수, `$1`과 `$2`는 각각의 값입니다. PID 형식·도구·프로세스 존재를 확인한 뒤 파일을 엽니다. `set -u`는 미설정 변수 사용을 오류로 잡고, `LC_ALL=C`는 ps 숫자 등 출력 형식을 일정하게 하는 데 사용합니다.

```bash
set -C
if ! exec 3>"$log_file"; then
    # 오류 출력 후 종료
fi
```

`set -C`는 일반 파일 덮어쓰기를 방지합니다. 여기서 `exec`는 다른 프로그램으로 교체하는 용도가 아니라 관제 셸의 파일 디스크립터 3을 여는 용도입니다. 이후 `>&3`으로 같은 파일에 기록하며 관제 프로세스 종료 시 디스크립터도 닫힙니다. `!`는 성공·실패 판정을 뒤집으므로 파일 열기가 실패한 경우에 오류 분기로 들어갑니다.

#### 7. 시간과 ps 수치를 한 행씩 기록한다

[monitor.sh 41~65행](../monitor.sh#L41), 관제 루프.

`date`로 현지 날짜·시간을 만들고 `ps -p "$pid" -o %cpu=,rss=,%mem=,stat=`로 네 값을 읽습니다. 각 필드 뒤 `=`는 ps 헤더를 생략합니다. `read -r ... <<< "$sample"`은 문자열을 입력으로 공급하고 공백으로 나눠 네 변수에 담습니다. `-r`은 역슬래시를 이스케이프로 해석하지 않도록 합니다.

| CSV 열 | 의미 | 해석 주의 |
| --- | --- | --- |
| date_local, time_local | 관측한 Linux 현지 날짜·시간 | 앱 로그와 같은 시간 기준으로 비교 |
| pid | 관제 프로세스 | 다른 실행 PID와 혼동하지 않기 |
| cpu_percent_lifetime | 프로세스 시작 이후 평균 CPU 사용률 | 순간 CPU 피크를 대표하지 않음 |
| rss_kib | 메모리에 상주하는 프로세스 메모리 크기(KiB) | 앱이 출력한 Heap 값과 별개의 지표 |
| mem_percent_system | 시스템 물리 메모리 대비 비율 | MEMORY_LIMIT 사용 비율이 아님 |
| status | 관제 스크립트가 붙인 RUNNING/EXITED | RUNNING은 업무 진행·정상 응답을 보장하지 않음 |

날짜 문자열에 이미 쉼표가 하나 들어 있어 printf에 전달하는 인자는 여섯 개여도 CSV 열은 일곱 개입니다. 헤더가 지표의 의미와 단위를 담으므로 이후 비교 실험에서 해석을 유지할 수 있습니다.

#### 8. 종료와 관측 실패를 구분한다

[monitor.sh 55~81행](../monitor.sh#L55)은 좀비(Z)·종료 상태(X)를 EXITED로 처리합니다. ps가 실패했을 때 `/proc/PID`도 없으면 프로세스 소멸로 보고 수치가 빈 EXITED 행을 남깁니다. `/proc/PID`가 있는데 읽기에 실패하면 관측 오류로 종료합니다. 측정하지 못한 수치를 0으로 꾸며 기록하지 않습니다.

프로세스가 살아 있으면 기록 후 `sleep 1`하고 다시 읽습니다. 실제 주기는 명령 수행 시간도 포함하므로 정확히 1초 간격을 보장하는 타이머는 아닙니다. 각 행의 실제 시각으로 해석해야 합니다. 관제 종료 행만으로는 앱의 종료 원인을 알 수 없으므로 app.log를 함께 확인합니다.

#### 9. CSV는 저장 형식이고 column은 화면 표시다

```bash
column -s, -t "$run_dir/monitor.csv"
```

쉼표를 기준으로 열을 나누고 표처럼 정렬합니다. 원본 CSV는 바뀌지 않습니다. `.log`에는 정해진 문법이 없지만 현재 CSV는 열 의미가 고정되어 수치 추출·스프레드시트 활용에 적합합니다. `column`은 관제의 필수 도구가 아니며 없으면 `cat`으로 원본을 읽을 수 있습니다. 앱의 자유로운 메시지는 app.log에 원문으로 둡니다. 관련 실행 안내는 [README](../README.md)의 관제 및 증거 수집 절에 있습니다.

### 제약·예외·고려사항

**재준비 실패 후 남은 값:** [prepare-env.sh 157~164행](../prepare-env.sh#L157)의 실패 안내는 리뷰 Minor-1을 반영했습니다. source는 현재 셸에서 실행되므로 새로운 준비가 초기에 실패하면 예전 run_dir과 PID가 남습니다. 반대로 앱을 시작한 뒤 자식 확인에서 실패할 수도 있습니다. 남은 변수만으로 성공·미실행을 단정하지 않고 오류와 실제 상태를 확인합니다. 변수 삭제 대신 안내를 선택한 이유는 중복 실행 방지와 진단 정보를 보존하기 위해서입니다.

**Ctrl+C와 앱:** 현재 대화형 Bash 사용 흐름에서 앱은 백그라운드, 관제는 포그라운드 작업입니다. Ctrl+C로 관제를 중단한 직후 앱 PID가 살아 있음을 사용자 실행으로 확인했습니다. 모든 셸 설정·프로세스 그룹 구성에서도 동일하다고 일반화하지 않습니다. 관제를 중단한 파일은 EXITED 행 없이 끝날 수 있으며, 이것만으로 앱 종료를 추정하면 안 됩니다.

**파일과 실패:** 실행별 디렉터리와 noclobber는 이전 증거 보존을 돕습니다. 파일 생성 오류와 수집 중 쓰기 오류는 별개입니다. 이번에는 기존 파일 거부와 잘못된 경로 생성 실패를 실행 확인했고, 디스크 부족 같은 모든 장애를 재현하지는 않았습니다. 실패 전에 일부 데이터가 저장되어 있을 수도 있습니다. `/runs/`는 [.gitignore](../.gitignore)에서 제외되므로 최종 보고서에 쓸 증거를 별도로 포함해야 합니다.

**관측 한계:** 이 스크립트는 자식 하나를 관제하고 자동 재시작·종료·정리를 하지 않습니다. 프로세스의 생존과 업무 진행은 다르며, Deadlock은 PID·스레드 상태·변화 정체·마지막 로그를 함께 봐야 합니다. CPU 분석에서는 구간별 top 등의 출력도 필요합니다.

#### 이번 사용자 실행으로 확인한 결과

| 확인 | 실제 결과 | 결론의 범위 |
| --- | --- | --- |
| 준비 설정 오류 | MEMORY_LIMIT=49, 반환값 1, 이전 변수 유지 및 추가 안내 | 해당 입력 실패 경로 확인 |
| CSV와 column | PID 12158, RSS 18,504 → 274,544 KiB, 7열 정렬 | 수치 수집과 표시 확인 |
| 종료 증거 연결 | 22:15:15.802 PID 12158 자체 종료 로그, 22:15:16 CSV EXITED | MemoryGuard 자체 종료 확인 |
| 기존 CSV 보호 | 생성 거부, 반환값 1, 전후 SHA-256 동일 | 해당 파일 내용 보존 |
| 생성 실패 | /dev/null/monitor.csv에 Not a directory, 반환값 1 | 잘못된 경로 생성 실패 처리 |

`SN`의 S는 인터럽트 가능한 대기 상태, N은 낮은 우선순위 표시입니다. 이것만으로 교착상태라고 판단하지 않습니다. MemoryGuard 로그는 Heap 275MB가 한도 256MB를 초과했다고 알렸습니다. CSV의 RSS는 다른 지표이고 샘플 시각도 달라 두 숫자가 일치할 필요가 없습니다. 셸의 Killed 한 단어만으로 OS OOM Killer 작동이라고 단정하지 않습니다.

### 동료평가에서 스스로 설명해 보기

아래 질문에 먼저 자기 말로 답한 뒤 근거를 확인하세요. 실제 평가 출제를 보장하는 질문은 아닙니다.

1. 왜 준비는 source이고 관제는 bash 실행인가요?
2. 입력 프롬프트가 돌아왔는데 앱은 어떻게 계속 실행되나요? 부모 PID와 관제 PID는 왜 다른가요?
3. MEMORY_LIMIT를 49로 바꾸면 어떤 순서로 실패하며 run_dir은 어떻게 되나요?
4. CSV의 MEM 1.6%를 한도 256MB의 1.6%라고 말해도 되나요?
5. 기존 CSV 이름을 다시 전달했을 때 어떤 장치가 파일을 보호하나요?
6. 프로세스가 없어졌는데 메모리를 0으로 기록하지 않는 이유는 무엇인가요?
7. 관제가 RUNNING이라고 기록하면 앱이 정상 응답하고 있다는 뜻인가요?
8. 한도를 높여 오래 살아 있으면 메모리 누수가 해결된 것인가요?

답변 근거:

- 1~2: [prepare-env.sh 4~7행](../prepare-env.sh#L4)과 [`codyssey_prepare_env` 115~145행](../prepare-env.sh#L115). 부모 셸에 남길 값, export의 상속, 백그라운드 실행과 직접 자식 선택을 설명합니다.
- 3: [`codyssey_prepare_env` 60~65행](../prepare-env.sh#L60)과 [최종 실패 분기 160~164행](../prepare-env.sh#L160). 허용 범위 밖이면 새 경로 할당 전에 반환하며 이전 값이 남을 수 있습니다.
- 4: [monitor.sh 36행 헤더](../monitor.sh#L36)와 [48행 ps 필드](../monitor.sh#L48). %MEM은 시스템 물리 메모리 기준이고 RSS와 Heap은 동일 지표가 아닙니다.
- 5~6: [monitor.sh 29~39행](../monitor.sh#L29) 및 [66~71행](../monitor.sh#L66). 파일 생성 거부와 미측정 빈 필드를 설명합니다.
- 7: [monitor.sh 55~60행](../monitor.sh#L55). RUNNING 분류는 Z/X 이외 상태를 묶으며 응답 여부를 검사하지 않습니다.
- 8: [MISSION](harness/MISSION.md)의 메모리 요구사항. 한도 증가는 임시 조치이며 메모리 증가 원인을 없앤다는 뜻은 아닙니다. 실제 전후 생존 시간 비교는 다음 단계입니다.

### 남은 질문과 다음 학습

사용자가 질문했던 CSV/LOG 차이, column 조회, 터미널과 앱 생존, source 실패 후 이전 변수, 사용자 검증 명령의 의미를 위에 보완했습니다. 읽고 이해했는지는 아직 확인하지 않았습니다.

현재 구현된 실제 TASK는 TASK-001 하나입니다. 누락 학습 보완 순서는 ① 셸과 환경변수 ② 실행·부모/자식 PID ③ 관제 수치와 파일 보호 ④ 로그 연결·실패 안내 ⑤ 동료평가 질문입니다. 이번 문서가 이 순서의 자료를 제공합니다.

다음 학습은 MEMORY_LIMIT 변경 전후 비교입니다. 메모리 구조·누수의 시스템 영향·근본 원인 추론은 그 실험과 함께 더 자세히 보완합니다. CPU 과점유·Deadlock 설명은 해당 TASK가 진행될 때 같은 파일에 추가합니다. 구현·리뷰·사용자 테스트는 완료된 범위로 기록하며, 미션 전체 완료나 사용자 이해 완료로 확대하지 않습니다.
