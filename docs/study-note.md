## TASK-001: Linux 실행 환경 및 관제 준비

### 미션에서 이번 단계의 위치

첫 단계에서는 장애를 고치는 대신 장애를 관찰할 준비를 했습니다. 제공 바이너리는 분석 대상이고, 직접 만든 셸 스크립트는 실행 조건과 증거 수집을 돕습니다. 관측할 PID나 로그가 잘못되면 이후 원인 분석도 잘못되므로, 실행별 로그 분리와 실제 작업 프로세스 식별이 먼저 필요합니다.

관련 자료: [TASK-001](harness/tasks/TASK-001.md), [사용 방법](../README.md), [독립 리뷰](harness/reviews/REVIEW-TASK-001.md), [실제 검증 기록](harness/WORKLOG.md).

### 먼저 이해할 개념

**터미널·셸·프로세스:** 터미널은 입력과 출력을 보여 주고, Bash 셸이 명령을 해석합니다. 바이너리를 실행하면 프로세스가 생깁니다. 입력 프롬프트가 보인다고 백그라운드 앱까지 종료된 것은 아닙니다.

**PID와 PPID:** PID는 프로세스 번호, PPID는 부모 프로세스 번호입니다. 제공 실행 파일은 별도의 작업 자식을 생성하는 것으로 관찰됐습니다. 이번 관제는 그 자식을 대상으로 합니다. 시간이 지나면 PID가 재사용될 수 있어 숫자만 장기간 보관하지 않고 실행 디렉터리와 함께 해석합니다.

**셸 변수와 환경변수:** `run_dir`은 현재 셸이 다음 명령에서 참조하는 값입니다. `export MEMORY_LIMIT=256`처럼 내보낸 변수는 이후 실행하는 자식 프로그램이 물려받습니다. 자식에서 값을 바꾼다고 부모 셸 값이 자동 변경되지는 않습니다.

**source와 bash 실행:** `source ./prepare-env.sh`는 현재 셸에서 파일을 읽으므로 PID와 경로가 뒤의 명령에도 남습니다. `bash ./monitor.sh ...`는 별도 Bash에서 관제를 실행합니다. 따라서 monitor의 `set -u`, `set -C`, `LC_ALL=C`는 그 관제 프로세스 환경에 적용됩니다.

**종료 상태:** 관례상 반환값 0은 성공, 0이 아니면 실패입니다. `$?`는 바로 앞 명령의 종료 상태이므로 다른 명령을 실행하기 전에 읽어야 합니다. `A && B`는 A가 성공했을 때만 B를 실행합니다. 다음 줄에 별도로 쓴 C까지 조건부로 만드는 것은 아닙니다.

### 실행 흐름을 따라 코드 읽기

#### 1. 현재 셸에서 준비 함수를 호출한다

입력은 다음과 같습니다. 여기의 명령은 사용 흐름 설명이며 지금 다시 실행할 필요는 없습니다.

```bash
source ./prepare-env.sh && bash ./monitor.sh "$app_pid" "$run_dir/monitor.csv"
```

[prepare-env.sh 4~7행](../prepare-env.sh#L4)은 `BASH_SOURCE[0]`과 `$0`을 비교해 직접 실행을 거부합니다. `source`일 때는 함수 정의를 읽고 [157행](../prepare-env.sh#L157)에서 `codyssey_prepare_env`를 호출합니다. 함수가 0을 반환해야 `&&` 뒤의 관제가 시작됩니다. 큰따옴표는 경로에 공백이 있어도 하나의 인자로 전달되도록 합니다.

#### 2. 중복 실행과 환경 오류를 먼저 확인한다

[prepare-env.sh 14~58행](../prepare-env.sh#L14)의 `codyssey_prepare_env`은 필요한 도구, 기존 PID, OS, UID, 아키텍처, 실행 권한, 포트를 확인합니다. `command -v`는 명령 존재를, `ps -p`는 PID 존재를 확인합니다. `ss`는 15034번 포트의 수신 소켓을 조회합니다. 포트 검사는 이 순간의 상태일 뿐 실제 bind 성공까지 보장하지 않으므로 앱 부트 로그도 봐야 합니다.

`$(uname -m)`은 명령 출력을 변수에 담는 명령 치환입니다. `case`는 아키텍처에 맞는 바이너리를 고릅니다. macOS 호스트의 칩 이름 대신 실제 Linux 머신의 응답을 사용합니다. 확인 실패 시 `return 1`로 함수와 준비 절차를 중단하며, 현재 대화형 셸 자체를 종료하지 않습니다.

#### 3. 설정값을 검증하고 필요한 경로를 준비한다

[prepare-env.sh 60~102행](../prepare-env.sh#L60), `codyssey_prepare_env`.

```bash
selected_memory=${MEMORY_LIMIT:-256}
```

`${변수:-기본값}`은 변수가 없거나 비었을 때 기본값을 사용합니다. 예를 들어 설명용 입력 `MEMORY_LIMIT=49`는 문자열 모양 검사에는 맞지만 50~512 범위 검사에 실패합니다. `[[ ... =~ ... ]]`는 정규식 검사, `(( ... ))`는 정수 연산입니다. `10#`은 숫자를 10진수로 해석하도록 지정합니다. 코드가 값의 모양을 먼저 검사하므로 잘못된 문자열을 곧바로 산술식에 넣지 않습니다.

`local` 변수는 함수 내부 준비값이며, 검증된 값은 나중에 전역 변수와 환경변수로 전달합니다. `mkdir -p`는 필요한 디렉터리를 준비합니다. 기존 키가 있으면 `cmp`로 공개 시험용 값과 비교하고 덮어쓰지 않습니다. `-L` 검사로 심볼릭 링크가 있는 경우도 새 파일 생성 경로에서 제외합니다.

키를 만들 때 `(set -C; printf ... > "$key_file")`의 괄호는 서브셸입니다. 덮어쓰기 방지 옵션을 그 작은 작업에만 적용해 사용자의 현재 셸 옵션을 바꾸지 않습니다. 여기의 키는 미션에서 공개한 시험용 값이며 실제 서비스 인증정보와 구분해야 합니다.

#### 4. 새 로그 공간을 확보한 다음 앱을 시작한다

[prepare-env.sh 104~128행](../prepare-env.sh#L104), `codyssey_prepare_env`.

`mktemp -d`는 실행별 디렉터리를 생성합니다. 날짜만 사용하면 같은 초의 실행끼리 이름이 겹칠 수 있으므로 임의 접미사가 붙습니다. 앱 로그에 시작 시각을 기록한 다음 환경변수를 export하고 `run_dir`을 새 경로로 갱신합니다.

```bash
"$binary" >> "$run_dir/app.log" 2>&1 &
launcher_pid=$!
```

`>>`는 표준 출력(1)을 파일에 이어 씁니다. 그 뒤 `2>&1`은 표준 오류(2)도 같은 출력 대상으로 보냅니다. 마지막 `&`는 백그라운드 실행이고 `$!`는 방금 시작한 비동기 작업의 PID입니다. 셸은 앱 종료를 기다리지 않고 PID 확인 단계로 넘어갑니다. 앱의 로그와 준비 스크립트의 터미널 안내는 서로 다른 출력입니다.

#### 5. 부모가 만든 실제 작업 자식을 관제 대상으로 고른다

[prepare-env.sh 130~154행](../prepare-env.sh#L130)의 `codyssey_prepare_env`은 부모가 살아 있는지 확인하고 `ps --ppid`로 직접 자식을 찾습니다. 자식 하나만 식별될 때 정규식 캡처 `BASH_REMATCH[1]`을 `app_pid`에 넣습니다. 자식이 없으면 최대 다섯 번 조회하며 사이에 기다립니다. 여러 자식이 나오면 임의로 선택하지 않고 오류를 반환합니다.

예를 들어 실제 실행에서 부모는 12153, 작업 자식은 12158이었습니다. `$!`로 얻은 부모만 관제하면 우리가 찾는 메모리 증가를 놓칠 수 있습니다. `Started (boot unverified)`는 PID 식별 성공이지 앱 내부의 모든 부트 조건 통과 판정은 아닙니다.

#### 6. 관제 인자를 확인하고 새 CSV를 연다

[monitor.sh 3~39행](../monitor.sh#L3), 최상위 준비 단계.

입력은 대상 PID와 새 로그 경로 두 개입니다. `$#`는 인자 개수, `$1`과 `$2`는 각각의 값입니다. PID 형식·도구·프로세스 존재를 확인한 뒤 파일을 엽니다. `set -u`는 미설정 변수 사용을 오류로 잡고, `LC_ALL=C`는 ps 숫자 등 출력 형식을 일정하게 하는 데 사용합니다.

```bash
set -C
if ! exec 3>"$log_file"; then
    # 오류 출력 후 종료
fi
```

`set -C`는 일반 파일 덮어쓰기를 방지합니다. 여기서 `exec`는 다른 프로그램으로 교체하는 용도가 아니라 관제 셸의 파일 디스크립터 3을 여는 용도입니다. 이후 `>&3`으로 같은 파일에 기록하며 관제 프로세스 종료 시 디스크립터도 닫힙니다. `!`는 성공·실패 판정을 뒤집으므로 파일 열기가 실패한 경우에 오류 분기로 들어갑니다.

#### 7. 시간과 ps 수치를 한 행씩 기록한다

[monitor.sh 41~65행](../monitor.sh#L41), 관제 루프.

`date`로 현지 날짜·시간을 만들고 `ps -p "$pid" -o %cpu=,rss=,%mem=,stat=`로 네 값을 읽습니다. 각 필드 뒤 `=`는 ps 헤더를 생략합니다. `read -r ... <<< "$sample"`은 문자열을 입력으로 공급하고 공백으로 나눠 네 변수에 담습니다. `-r`은 역슬래시를 이스케이프로 해석하지 않도록 합니다.

| CSV 열 | 의미 | 해석 주의 |
| --- | --- | --- |
| date_local, time_local | 관측한 Linux 현지 날짜·시간 | 앱 로그와 같은 시간 기준으로 비교 |
| pid | 관제 프로세스 | 다른 실행 PID와 혼동하지 않기 |
| cpu_percent_lifetime | 프로세스 시작 이후 평균 CPU 사용률 | 순간 CPU 피크를 대표하지 않음 |
| rss_kib | 메모리에 상주하는 프로세스 메모리 크기(KiB) | 앱이 출력한 Heap 값과 별개의 지표 |
| mem_percent_system | 시스템 물리 메모리 대비 비율 | MEMORY_LIMIT 사용 비율이 아님 |
| status | 관제 스크립트가 붙인 RUNNING/EXITED | RUNNING은 업무 진행·정상 응답을 보장하지 않음 |

날짜 문자열에 이미 쉼표가 하나 들어 있어 printf에 전달하는 인자는 여섯 개여도 CSV 열은 일곱 개입니다. 헤더가 지표의 의미와 단위를 담으므로 이후 비교 실험에서 해석을 유지할 수 있습니다.

#### 8. 종료와 관측 실패를 구분한다

[monitor.sh 55~81행](../monitor.sh#L55)은 좀비(Z)·종료 상태(X)를 EXITED로 처리합니다. ps가 실패했을 때 `/proc/PID`도 없으면 프로세스 소멸로 보고 수치가 빈 EXITED 행을 남깁니다. `/proc/PID`가 있는데 읽기에 실패하면 관측 오류로 종료합니다. 측정하지 못한 수치를 0으로 꾸며 기록하지 않습니다.

프로세스가 살아 있으면 기록 후 `sleep 1`하고 다시 읽습니다. 실제 주기는 명령 수행 시간도 포함하므로 정확히 1초 간격을 보장하는 타이머는 아닙니다. 각 행의 실제 시각으로 해석해야 합니다. 관제 종료 행만으로는 앱의 종료 원인을 알 수 없으므로 app.log를 함께 확인합니다.

#### 9. CSV는 저장 형식이고 column은 화면 표시다

```bash
column -s, -t "$run_dir/monitor.csv"
```

쉼표를 기준으로 열을 나누고 표처럼 정렬합니다. 원본 CSV는 바뀌지 않습니다. `.log`에는 정해진 문법이 없지만 현재 CSV는 열 의미가 고정되어 수치 추출·스프레드시트 활용에 적합합니다. `column`은 관제의 필수 도구가 아니며 없으면 `cat`으로 원본을 읽을 수 있습니다. 앱의 자유로운 메시지는 app.log에 원문으로 둡니다. 관련 실행 안내는 [README](../README.md)의 관제 및 증거 수집 절에 있습니다.

### 제약·예외·고려사항

**재준비 실패 후 남은 값:** [prepare-env.sh 157~164행](../prepare-env.sh#L157)의 실패 안내는 리뷰 Minor-1을 반영했습니다. source는 현재 셸에서 실행되므로 새로운 준비가 초기에 실패하면 예전 run_dir과 PID가 남습니다. 반대로 앱을 시작한 뒤 자식 확인에서 실패할 수도 있습니다. 남은 변수만으로 성공·미실행을 단정하지 않고 오류와 실제 상태를 확인합니다. 변수 삭제 대신 안내를 선택한 이유는 중복 실행 방지와 진단 정보를 보존하기 위해서입니다.

**Ctrl+C와 앱:** 현재 대화형 Bash 사용 흐름에서 앱은 백그라운드, 관제는 포그라운드 작업입니다. Ctrl+C로 관제를 중단한 직후 앱 PID가 살아 있음을 사용자 실행으로 확인했습니다. 모든 셸 설정·프로세스 그룹 구성에서도 동일하다고 일반화하지 않습니다. 관제를 중단한 파일은 EXITED 행 없이 끝날 수 있으며, 이것만으로 앱 종료를 추정하면 안 됩니다.

**파일과 실패:** 실행별 디렉터리와 noclobber는 이전 증거 보존을 돕습니다. 파일 생성 오류와 수집 중 쓰기 오류는 별개입니다. 이번에는 기존 파일 거부와 잘못된 경로 생성 실패를 실행 확인했고, 디스크 부족 같은 모든 장애를 재현하지는 않았습니다. 실패 전에 일부 데이터가 저장되어 있을 수도 있습니다. `/runs/`는 [.gitignore](../.gitignore)에서 제외되므로 최종 보고서에 쓸 증거를 별도로 포함해야 합니다.

**관측 한계:** 이 스크립트는 자식 하나를 관제하고 자동 재시작·종료·정리를 하지 않습니다. 프로세스의 생존과 업무 진행은 다르며, Deadlock은 PID·스레드 상태·변화 정체·마지막 로그를 함께 봐야 합니다. CPU 분석에서는 구간별 top 등의 출력도 필요합니다.

### 먼저 이해할 개념

프로세스는 가상 주소 공간에 실행 코드, 전역 데이터, 함수 호출에 필요한 스택, 동적으로 쓰는 힙 등을 둡니다. 가상 주소 공간의 크기 전체가 물리 메모리에 올라와 있는 것은 아닙니다. RSS는 현재 물리 메모리에 상주한 프로세스 페이지의 크기입니다. 앱 로그의 Heap은 앱이 자체 보고한 지표이며 RSS와 범위·단위·측정 시점이 다릅니다. CSV의 시스템 대비 메모리 비율도 앱 한도의 소진율이 아닙니다.

필요 없어진 데이터를 계속 보유하면 메모리 여유가 줄고 다른 프로세스·캐시에 영향을 줄 수 있습니다. 상황에 따라 회수·스왑으로 지연이 생기거나 시스템의 메모리 부족 처리가 필요해질 수 있습니다. 이번 관측은 지속적인 메모리 증가를 보여주지만 어떤 객체가 해제되지 않는지까지 증명하지는 않습니다. 앱 내부를 분석하지 않는 미션 제약 아래 관측 사실과 추론을 구분합니다.

MemoryGuard는 앱의 보호 정책입니다. 앱이 한도 초과와 자체 종료를 기록했고 같은 PID가 EXITED로 관측됐다는 것이 근거입니다. OS OOM Killer는 커널의 메모리 부족 처리와 관련된 별도 개념입니다. 셸의 Killed 메시지만으로 커널이 메모리 부족 때문에 종료했다고 단정하지 않습니다. 한도를 올리는 것은 증가 원인을 고치는 조치가 아니며 종료를 늦추는 임시 조치입니다.

### 로그 네 종류와 시험용 키

| 파일 | 출처 | 가공·추가 내용과 용도 |
| --- | --- | --- |
| agent_app.log | 제공 바이너리의 자체 파일 로그 | 앱 내부 이벤트 원본. 스크립트는 AGENT_LOG_DIR로 저장 디렉터리 지정 |
| app.log | 바이너리 표준 출력·오류를 준비 스크립트가 저장 | 맨 앞 launch_local만 추가. 부트·READY·Resource Check·시간·INFO 등의 출력 형식은 바이너리가 제공 |
| monitor.csv | monitor.sh가 ps로 외부 관측 | 시각·PID·CPU·RSS·시스템 메모리 비율·RUNNING/EXITED를 CSV로 구성 |
| output.log | 비교 스크립트 출력 수집 | 설정·원본 경로·PID·진행 기록·로그 발췌·계산 결과·종료 코드 |

[prepare-env.sh 109~126행](../prepare-env.sh#L109)의 `"$binary" >> "$run_dir/app.log" 2>&1 &`는 앱 출력을 그대로 파일로 보냅니다. agent_app.log를 읽거나 변환하는 명령이 아닙니다. `>>`는 추가 기록, `2>&1`은 표준 오류를 현재 표준 출력과 같은 곳으로 보내기, 마지막 `&`는 백그라운드 실행입니다. 바이너리의 두 출력 경로에 같은 이벤트가 포함되어 두 파일 내용이 겹칩니다. 내부 로깅 구현은 확인하지 않았습니다.

Resource Check는 적용 설정에 대한 앱의 검사 화면입니다. 예를 들어 MEMORY 256MB와 CPU 80%는 현재 사용량이 아니라 설정값입니다. READY도 시작 검사 성공이지 이후 장애가 없다는 보장이 아닙니다. 실제 사용 추이는 앱 이벤트와 CSV를 함께 읽습니다.

[prepare-env.sh 80~100행](../prepare-env.sh#L80)은 `$AGENT_HOME/api_keys/secret.key`를 준비합니다. 다운로드한 인증서나 바이너리가 발급한 키가 아니라 원문이 지정한 공개 시험용 내용 `agent_api_key_test`를 넣는 파일입니다. 현재 비교 스크립트의 기본 AGENT_HOME은 `$HOME/agent-leak-lab`여서 저장소 밖에 생깁니다. 없는 경우만 생성하고 기존 파일은 덮어쓰지 않으며 내용이 다르면 실패합니다. 실제 서비스 credential을 사용하거나 저장소에 넣는 기능이 아닙니다.

### 실행 흐름을 따라 코드 읽기

#### 1. 설정과 비교 로그 공간을 준비한다

사용자는 저장소 루트에서 `./run-memory-comparison.sh`를 실행합니다. [10~48행](../run-memory-comparison.sh#L10)은 128/256MB, CPU 80%, 멀티스레드 false와 경로를 지정하고 입력·도구를 검사합니다. 동일한 두 한도는 비교 의미가 없으므로 거부합니다. `10#$limit`은 숫자를 십진수로 해석하는 Bash 산술 표기입니다. `set -u`는 없는 변수 사용을 오류로 처리하지만 모든 명령 실패를 자동 처리하는 옵션은 아니므로 명시적인 반환값 검사가 필요합니다.

함수 정의 자체는 실험을 시작하지 않습니다. 최상위 [138~152행](../run-memory-comparison.sh#L138)에서 `mktemp -d`로 고유 비교 디렉터리를 만들고 `set -C`로 새 output.log를 생성합니다. 기존 비교 증거를 덮어쓰지 않으려는 처리입니다. 설정 검사·디렉터리 생성처럼 이보다 앞에서 발생한 오류는 아직 output.log가 없어 터미널에만 남을 수 있습니다.

#### 2. 비교 설정을 저장하고 before를 시작한다

최상위 [196~202행](../run-memory-comparison.sh#L196)이 `run_comparison`을 호출합니다. [154~167행](../run-memory-comparison.sh#L154)은 설정을 `tee -a`로 화면과 파일에 동시에 보내고 설정 저장 실패 시 앱을 시작하지 않습니다. 이어 [171행](../run-memory-comparison.sh#L171)에서 `run_case before 128`의 표준 출력·오류를 tee로 전달합니다.

[`run_case` 50~63행](../run-memory-comparison.sh#L50)의 함수 본문은 `(...)` 서브셸입니다. 설정은 export로 앱에 상속하지만 해당 실행의 PID·run_dir 변수는 다음 실행과 분리합니다. 그 안에서 `source ./prepare-env.sh`를 사용해야 준비 스크립트가 만든 변수를 같은 실행에서 읽을 수 있습니다. [준비 도구 104~145행](../prepare-env.sh#L104)은 새 실행 폴더와 app.log를 만들고 앱을 시작한 뒤 관제할 자식 PID를 찾습니다. 실패하면 `return 1`로 해당 실행을 끝냅니다.

#### 3. 자식을 관측하고 수치를 계산한다

[65~70행](../run-memory-comparison.sh#L65)이 자식 PID와 새 CSV 경로를 [monitor.sh](../monitor.sh)에 넘깁니다. 관제는 별도 Bash 프로세스에서 실행하며 종료 관측까지 호출자가 기다립니다. CSV는 바이너리가 제공한 수치가 아니라 `ps`로 수집한 값입니다. 관제 실패는 비교 실패로 반환하지만 남은 앱을 자동으로 죽이지 않습니다.

[72~105행](../run-memory-comparison.sh#L72)은 `awk -F,`로 첫 RUNNING과 EXITED의 시각을 찾고 `date -d ... +%s`로 초 단위 시각으로 바꿔 차이를 계산합니다. 쉼표 기준 다섯 번째 열이 RSS, 일곱 번째가 상태입니다. RUNNING 행의 숫자 RSS 중 최댓값을 구하고 일부 CSV 행과 앱 로그 앞 25행·뒤 15행을 출력합니다. 이 발췌는 원본 전체를 대체하지 않습니다.

#### 4. 부트 성공과 다음 실행 가능 여부를 확인한다

[108~113행](../run-memory-comparison.sh#L108)은 앱 로그에서 `All Boot Checks Passed!`와 `Agent READY` 두 줄을 검사합니다. `grep -F`는 문자열 그대로, `-x`는 행 전체 일치, `-q`는 일치 여부만 반환합니다. `! 검사1 || ! 검사2`는 어느 하나라도 실패하면 오류 분기로 들어갑니다. 파일 읽기 실패도 성공으로 취급하지 않습니다.

이 검사는 관제 종료 후 수행합니다. PID가 한때 존재했고 CSV가 생겼다는 것만으로 앱 부트가 성공했다고 볼 수 없어서 추가했습니다(Major-1). 부트 성공 뒤 MemoryGuard가 종료한 경우 두 표식은 남아 있으므로 실험 실패와 구분됩니다. 앱 종료 원인을 자동 확정하는 검사는 아닙니다.

[117~135행](../run-memory-comparison.sh#L117)은 부모·자식 상태와 포트 15034를 최대 5회 확인합니다. 프로세스가 없거나 Z/X 상태이고 포트가 비었을 때 성공합니다. 남아 있으면 다음 실행을 막고 사람이 상태를 확인하도록 합니다. 프로세스 강제 종료·자동 재시작은 없습니다.

#### 5. before 실행과 저장이 모두 성공해야 after로 넘어간다

[171~181행](../run-memory-comparison.sh#L171)의 파이프라인이 끝나면 즉시 `pipeline_status=("${PIPESTATUS[@]}")`로 두 종료 코드를 복사합니다. 배열 첫 값은 run_case, 둘째는 tee의 반환값입니다. 다른 명령을 실행하면 PIPESTATUS가 바뀌므로 즉시 저장해야 합니다. 파이프라인의 마지막 명령 상태만 검사하면 앱 준비·관제 실패를 놓칠 수 있습니다.

이전 버전은 before와 after 전체를 하나의 tee로 묶어 저장 실패를 둘 다 끝난 뒤에야 확인했습니다. 현재는 before의 실행 실패 또는 출력 저장 실패 시 `return 1`로 돌아가 [183행](../run-memory-comparison.sh#L183)의 after를 시작하지 않습니다(Major-2). after도 같은 절차를 수행하며 메모리 한도만 256MB로 바뀝니다. 첫 실행 도중 쓰기 실패가 났다고 즉시 앱을 종료하는 방식은 아니고, 해당 파이프라인이 끝난 뒤 다음 실행을 차단합니다.

#### 6. 결과와 원본을 연결한다

[196~217행](../run-memory-comparison.sh#L196)은 비교 함수의 성공 여부를 final_status로 바꾸고 완료 요약·종료 코드를 기록합니다. experiment_exit_code와 log_exit_code는 마지막으로 확인한 파이프라인 양쪽의 상태이며, final_exit_code는 스크립트 최종 결과입니다. 요약 또는 최종 코드 자체를 기록하지 못하면 stderr로 안내하고 1로 종료합니다. 저장 장치에 쓸 수 없으면 실패 안내까지 파일에 남긴다고 보장할 수는 없습니다.

모든 stderr가 output.log에 항상 들어가는 것도 아닙니다. run_case의 출력·오류는 tee로 수집하지만, tee 자체의 오류와 파이프라인 밖의 저장 실패 안내는 터미널에 출력될 수 있습니다. 그 경우 사용자에게 해당 오류만 추가로 요청할 수 있습니다. 정상 실행에서는 비교 로그 경로만 전달해 AI가 연결된 앱 로그와 CSV를 읽으면 됩니다.

### 실제 비교 결과와 보고서 읽기

[OOM 보고서](reports/oom.md)는 원본에 근거한 아래 두 비교를 분리합니다. runs/는 Git 제외이므로 제출용 보고서 자체에 핵심 로그·CSV 행이 포함되어 있습니다. 원문은 이 네 로그 파일명을 모두 제출하라고 요구하지 않고, 관제 수치·종료 로그·설정 전후 비교를 증거로 담은 보고서를 요구합니다.

| 비교 | 관측 결과 | 가능한 결론 |
| --- | --- | --- |
| 128→256MB | 동일 MemoryWorker 증가, 각각 Heap 150/275MB에서 MemoryGuard 자체 종료. 관측 17→33초, 최고 RSS 표본 146,520→274,628 KiB | 한도 상향 후 이번 실행에서 16초 더 오래 생존. 증가 원인은 해결되지 않음 |
| 256→512MB | 256MB는 MemoryGuard 종료, 512MB는 RSS 정체와 CpuWorker 임계치 위반 뒤 EXITED. 관측 32→30초 | 동일 메모리 작업의 수명 비교로 사용할 수 없음 |

보고서의 17/33초는 첫 RUNNING부터 EXITED 관측까지입니다. launch_local부터 계산한 시간이 아니며 실제 프로세스 수명과 차이가 있습니다. 표본 간격에는 명령 실행 시간도 포함되고 CSV는 초 단위이므로 정확히 매초 측정한다는 뜻도 아닙니다. 최고 표본 RSS는 실제 순간 최고값을 놓칠 수 있습니다.

512MB에서 왜 CpuWorker가 동작했고 설정 80%인데 50.75%에서 위반을 기록했는지는 외부 로그만으로 확정하지 않습니다. 실제 WATCHDOG 신호도 해당 기록에 없으므로 만들어 적지 않습니다. 관측 사실은 설정·PID·시각·로그 문구이며, 내부 객체 누수나 알고리즘에 대한 설명은 확인 범위 안에서 추론으로 구분합니다.

### 제약·예외·검증 상태

[독립 리뷰](harness/reviews/REVIEW-TASK-002.md)의 Major-1·Major-2와 README 상태 불일치 Minor-1은 현재 코드·문서에 반영됐습니다. PM은 변경 범위가 한정되고 각 실패 반환과 다음 호출 경계를 추적할 수 있어 추가 독립 리뷰를 SKIP으로 판단했습니다. 이는 실행 검증을 대신하지 않습니다.

128/256MB 사용자 원본과 보고서 수치는 확인됐습니다. 추가로 [2026-10-08 검증 기록](harness/WORKLOG.md#task-002-현재-수정본-정상-비교-확인)에 연결된 현재 수정본의 정상 비교도 확인했습니다. 이 실행의 관측 시간은 18초→32초이며, 보고서의 기존 17초→33초 실험과 구분합니다. 현재 수정본의 부트 표식 누락·before 저장 실패 시 after 미실행은 사용자 요청으로 실행 검증을 생략했으므로 미검증으로 남깁니다. 실제 검증 여부를 기능 구현·자료 작성·사용자 이해와 구분해 기록합니다.

실패 검증 때문에 기존 원본을 편집하거나 실제 디스크를 채우지 않습니다. 별도 임시 환경에서 부트 표식 없는 모의 출력, 저장 오류를 반환하는 모의 도구 등으로 분기를 확인할 수 있지만, 이번에는 사용자 선택에 따라 수행하지 않았습니다.

### 먼저 이해할 개념

프로세스는 실행 자원과 주소 공간을 가지며 스레드는 그 안의 실행 흐름입니다. PID는 프로세스를, TID는 각 스레드를 식별합니다. 같은 프로세스의 스레드들은 메모리를 공유하므로 스레드별 RSS를 더해 프로세스 메모리로 계산하지 않습니다.

락은 공유 자원을 동시에 다루지 못하도록 접근을 조정합니다. 락을 기다리는 스레드는 CPU를 계속 사용하지 않고 잠들 수 있습니다. 따라서 낮은 CPU·살아 있는 PID·대기 상태는 정상 유휴 상태에서도 가능하며, **서로가 보유한 자원을 기다리는 고리와 작업 정체**를 함께 확인해야 합니다. `wchan`은 커널 대기 위치이고 `futex_wait`만으로 락의 소유자나 교착을 알 수 없습니다.

### 실행 흐름을 따라 코드 읽기

#### 1. 입력을 받고 관측 시간부터 검사한다

```bash
bash ./run-deadlock-observation.sh 512 40 true
```

[최상위 입력 처리 3~28행](../run-deadlock-observation.sh#L3)은 source 실행을 거부하고 필수 인자 세 개와 선택 시간 하나를 받습니다. `${4:-60}`은 네 번째 값이 없거나 비었을 때 60을 선택합니다. 이 예에서 `$1=512`, `$2=40`, `$3=true`, `duration=60`입니다. 이 값의 해설은 입력 설명이고 별도 재실행 결과가 아닙니다.

시간은 15~300초의 15초 배수여야 하므로 `... true 20`은 준비·앱 실행 전에 상태 2로 끝납니다. `[[ ... =~ ... ]]`는 문자열 형식을, `(( ... ))`는 숫자 조건을 검사합니다. 메모리·CPU·멀티스레드 값 검사는 다음 준비 도구가 담당합니다.

#### 2. 같은 스크립트 셸에서 준비 도구를 호출해 PID와 경로를 받는다

[31행의 source](../run-deadlock-observation.sh#L30)는 세 인자를 [codyssey_prepare_env](../prepare-env.sh#L9)에 전달합니다. 이 함수는 Linux·일반 사용자·아키텍처·포트와 [75~86행의 설정 범위](../prepare-env.sh#L75)를 확인합니다. 준비가 실패하면 관측 스크립트도 상태 1로 종료하며 남아 있을 수 있는 PID·로그를 확인하도록 안내합니다.

[준비 함수 116~150행](../prepare-env.sh#L116)은 `mktemp -d`로 실행별 디렉터리를 만들고 환경변수를 export한 뒤 앱을 백그라운드로 시작합니다. `$!`는 방금 시작한 백그라운드 PID이므로 여기서는 `launcher_pid`이며, 직접 자식을 찾아 `app_pid`를 별도로 정합니다. true 실행에서는 launcher 9870, 관측 대상 자식 9875였습니다.

source를 썼으므로 `app_pid`·`run_dir` 값은 관측 스크립트 안에서 이어집니다. 바깥 사용자 터미널은 이 스크립트를 `bash`로 실행했으므로 그 변수들이 사용자 셸로 역전달되지는 않습니다. 준비 함수의 성공 안내도 `boot unverified`이며 부트 표식은 뒤에서 따로 확인합니다.

#### 3. 새 관측 파일을 열고 CSV 수집을 병행한다

[36~49행](../run-deadlock-observation.sh#L36)은 실행 디렉터리 안의 `thread-observation.txt`를 파일 디스크립터 3으로 엽니다. `set -C`는 noclobber로 기존 파일 덮어쓰기를 거부하고, `exec 3>...`는 이후 `>&3` 출력이 같은 파일로 가도록 연결합니다. 생성·쓰기 실패 시 오류를 남기며 앱이 이미 시작됐을 수 있음을 알립니다.

[51~52행](../run-deadlock-observation.sh#L51)의 `bash ./monitor.sh ... &`는 CSV 관제를 백그라운드로 시작하고 `$!`를 `monitor_pid`에 저장합니다. 앱 PID와 관제 PID는 별개입니다. 관제는 [monitor.sh 29~38행](../monitor.sh#L29)에서 새 CSV를 보호하며 열고, [41~81행](../monitor.sh#L41)에서 `ps` 수치를 기록하고 약 1초마다 반복합니다.

CSV의 RUNNING은 Z/X 이외의 프로세스 상태를 분류한 값이며 업무 응답을 검사한 결과가 아닙니다. Z/X 또는 프로세스 소멸은 EXITED로 기록합니다. 측정 실패를 임의의 0으로 채우지 않고 오류 또는 빈 필드로 구분하는 이유는 잘못된 증거를 만들지 않기 위해서입니다.

#### 4. 시각별 프로세스·스레드·로그를 같은 파일에 남긴다

[60~116행의 for 루프](../run-deadlock-observation.sh#L60)는 `elapsed=0`에서 시작해 15씩 증가합니다. `elapsed < duration`이므로 기본 60초에서는 약 0/15/30/45초에 네 표본을 쓰고 각 회차 후 15초를 기다립니다. 스레드 첫·마지막 표본 간 범위는 약 45초이며 60초에 다섯 번째 표본을 쓰지 않습니다. 명령 실행 시간이 더해지므로 정확한 간격은 저장된 시각으로 읽습니다.

먼저 PID 상태를 확인하고 `date`로 표본 시각을 붙입니다. [80행](../run-deadlock-observation.sh#L80)의 `ps -p`는 프로세스 표, [91행](../run-deadlock-observation.sh#L90)의 `ps -L`은 TID·상태·CPU·RSS·wchan 표, [101행](../run-deadlock-observation.sh#L101)의 `tail -n 8`은 마지막 앱 로그를 씁니다. `$(...)`는 명령 출력을 변수에 담고 `|| state=`는 조회 실패 시 이전 상태 문자열을 남기지 않습니다.

프로세스가 사라지거나 Z/X이면 자연 종료로 기록합니다. 표본 저장 실패 뒤에도 PID를 다시 살펴 앱 종료와 수집 오류를 구분하며, 살아 있는 대상의 조회·쓰기 실패는 관측 실패로 남깁니다. 마지막 로그가 여러 표본에서 같다는 사실은 정체 근거지만 이것 하나만으로 교착을 확정하지 않습니다.

#### 5. 관제만 정리하고 실제 종료 상태를 회수한다

[118~140행](../run-deadlock-observation.sh#L118)은 앱 생존 여부를 다시 살피고, 앱이 살아 있으면 자신이 시작한 `monitor_pid`에만 TERM을 요청합니다. 앱과 launcher에 종료 신호를 보내지 않는 이유는 수집 후에도 사용자가 상태를 확인할 수 있게 하기 위해서입니다. 자연 종료이면 관제가 EXITED를 기록하고 끝나는 흐름을 기다립니다.

`wait "$monitor_pid"`는 백그라운드 관제의 종료를 기다리고 상태를 받습니다. `if wait ...; then ... else monitor_result=$?`는 실패 직후 `$?`를 저장하므로 다른 명령이 덮어쓰지 않습니다. [142행](../run-deadlock-observation.sh#L141)은 상태 0 또는 **TERM 요청에 성공했고 상태가 143인 경우**만 허용합니다. 종료 요청 기록만으로 상태 1 같은 관제 오류까지 성공으로 처리했던 문제를 수정한 조건입니다.

#### 6. INT/TERM으로 wait가 끊겨도 관제 결과와 중단 신호를 구분한다

[56~57행의 trap](../run-deadlock-observation.sh#L56)은 등록 시 즉시 실행되는 코드가 아니라 신호 처리 시 실행할 문자열입니다. INT는 `interrupted=130`, TERM은 `interrupted=143`을 기록하고 `wait_interrupted=1`로 대기 중단 가능성을 표시합니다. 130/143은 각각 128+신호 번호 2/15에 해당하는 종료 코드입니다.

[131~140행](../run-deadlock-observation.sh#L131)은 매 대기 직전에 `wait_interrupted=0`으로 초기화합니다. trap이 실행됐다면 `wait` 반환이 관제 자체의 종료 상태가 아닐 수 있어 관제에 TERM을 요청하고 다시 기다립니다. trap으로 끊기지 않은 회수 결과를 위 허용 조건에 전달하는 것이 핵심이며, 부모 신호 때문에 나온 130/143을 관제의 실제 실패로 오인하지 않게 합니다.

신호 처리가 모든 시점에서 즉시 끝난다고 보장하지는 않습니다. Bash가 포그라운드 명령을 기다리는 시점 등에 따라 trap 실행 시점이 달라질 수 있으며, 실제 신호·경합 실행 검증은 남아 있습니다.

#### 7. 저장 근거와 부트 성공을 확인하고 사용자에게 상태를 돌려준다

[146~178행](../run-deadlock-observation.sh#L146)은 CSV 상태 행과 부트 성공 표식을 확인하고 파일 디스크립터를 닫은 뒤 증거 경로·PID·포트를 출력합니다. 중단이면 저장한 130/143, 그 외 수집 오류면 1을 반환하며, 정상 완료 메시지의 0은 관측 수집 성공을 뜻합니다. 앱 정상 응답 또는 교착 확정 판정은 아닙니다. 표식 문자열 검사는 이 앱의 부트 확인용이며 미션 예시 문구 전체를 강제하는 검사는 아닙니다.

### 실제 증거로 교착 원인을 설명하기

true 원본의 [agent_app.log 8~15행](../runs/261026-175455_512_40_true-kFiIRQ/agent_app.log#L8)을 먼저 읽고 [스레드 표 25행 이후](../runs/261026-175455_512_40_true-kFiIRQ/thread-observation.txt#L25)를 연결합니다. 자원 이름은 앱이 붙인 명칭입니다.

| 로그 스레드 | 먼저 획득한 락 | 나중에 기다리는 락 | 그 락을 먼저 가진 상대 |
| --- | --- | --- | --- |
| Worker-Thread-1 | Shared_Memory_A | Socket_Pool_B | Worker-Thread-2 |
| Worker-Thread-2 | Socket_Pool_B | Shared_Memory_A | Worker-Thread-1 |

각자 가진 락을 유지한 채 다음 락이 필요하고 상대도 같은 상황이므로 진행과 기존 락 해제로 이어질 처리가 막힌 구조로 추론합니다. 17:55:05.064 BLOCKED 이후 17:55:11·26·41에도 같은 마지막 로그와 세 TID의 `futex_wait`가 이어졌습니다. TID 9933/9934의 CPU는 각 0.0%였지만 로그 이름과 두 TID의 개별 대응은 확인하지 않았습니다.

네 조건으로 설명하면 **상호 배제**는 락의 독점 사용, **점유 대기**는 하나를 가진 채 추가 락 대기, **비선점**은 상대 락을 임의로 회수하지 못함, **순환 대기**는 서로의 자원을 기다리는 고리입니다. 이는 로그에 맞춘 원인 설명이며 내부 락 함수·타임아웃·해제 정책까지 확인한 것은 아닙니다. 대기는 종료가 아니어서 PID는 남고, 계산·후속 로그 작성이 진행되지 않아 CPU와 로그 변화가 줄 수 있습니다.

| 비교 항목 | true | false |
| --- | --- | --- |
| 조건·관측 대상 | 512MB / CPU 40% / 기본 60초, PID 9875 | 같은 조건, PID 10481 |
| CSV 첫~마지막 시각 | 17:54:56~17:55:56 | 18:00:03~18:01:02 |
| RSS 처음→마지막 (KiB) | 18,352→18,148; 중간 18,440 | 18,500→504,780 |
| 프로세스 수명평균 CPU 처음→마지막 | 4.0→0.0% | 5.0→1.8% |
| 작업과 로그 | 락 순환 대기 뒤 정체 | Healthy System Monitoring에서 지속 진행 |

true의 RSS는 소폭 감소했으므로 완전히 불변이라고 표현하지 않습니다. CPU는 `ps`의 수명평균으로 순간 부하나 앱 `Current Load`와 같은 지표가 아닙니다. 두 CSV 모두 마지막까지 RUNNING이므로 작업 진행 여부는 수치·로그·스레드를 함께 봐야 합니다.

false의 [앱 로그 3~22행](../runs/261026-180002_512_40_false-1munWl/agent_app.log#L3)은 Healthy 경로와 스케줄러 완료를 보여 줍니다. [OS 표본 25행 이후](../runs/261026-180002_512_40_false-1munWl/thread-observation.txt#L25)에는 메인 TID 10481의 `futex_wait`와 작업 TID 10512/10513의 대기·실행이 공존합니다. false여도 OS 스레드가 있으며 메인 대기만으로 앱 전체의 교착을 단정할 수 없습니다.

### 제약·예외·고려사항

설정 외 입력은 유지했지만 false에서는 앱 경로 자체가 바뀌었습니다. 따라서 관측 구간에서 교착을 회피했다는 결과이며 같은 락 알고리즘 수정·영구 무장애·모든 자원 문제 해결의 증거는 아닙니다. CSV 수집 뒤 18:01:06의 [cleanup 로그 67~68행](../runs/261026-180002_512_40_false-1munWl/agent_app.log#L67)는 60초 비교에서 RSS 감소를 검증한 결과로 섞지 않습니다.

파일 생성 실패·수집 중 쓰기 실패·부분 증거를 구분하고 원본을 보존합니다. 관측 종료 후 앱이 남을 수 있으므로 다음 실행 전에 실제 PID와 포트 및 종료 필요성을 확인합니다. 반환값 0·종료 출력의 PID·포트 확인과 실행 사이 종료는 [TASK의 사용자 확인 기록](harness/tasks/TASK-004.md)에 근거하며, 네 원본 파일에 종료 출력이 보존됐다고 주장하지 않습니다. Git 제외 원본은 다른 작업 공간에서 열리지 않을 수 있어 [보고서](reports/deadlock.md)에 핵심 발췌를 남겼습니다.

[도구 독립 리뷰·수정 재검토](harness/reviews/REVIEW-TASK-004.md)와 [보고서 독립 리뷰](harness/reviews/REVIEW-TASK-004-DEADLOCK-REPORT.md)는 완료됐고 사용자가 보고서를 확인했습니다. 시간 만료·관제 정리·앱 유지 정상 경로는 두 실행으로 확인했습니다. Ctrl+C/TERM·자연 종료·관제 실패 경합은 실행 미검증이며 독립 리뷰의 정적 확인으로 실행 성공을 추정하지 않습니다. 이 도구 검증을 미션 필수 실험으로 확대하지 않습니다.

### 동료평가에서 스스로 설명해 보기

1. PID가 있고 CPU가 낮은데 왜 장애일 수 있나요? `futex_wait` 하나로 판단해도 되나요?
2. 두 스레드가 왜 락을 놓지 못하나요? 내부 함수도 확인한 것인가요?
3. 60초 관측인데 스레드 표본은 왜 네 개이며, 시간을 20초로 주면 어떻게 되나요?
4. 관제에 TERM을 보냈는데 상태 1로 끝났다면 관측 성공인가요? wait 중 INT를 받으면요?

### 남은 질문과 다음 학습

학습 순서는 단일 명령의 준비·PID → 두 수집 흐름 → 관제 종료와 앱 유지 → 순환 대기 근거 → false 비교와 한계 → 동료평가 답변입니다. 사용자 질문이었던 “이번 원인이 정확히 무엇인가”는 위 A/B 락 점유·대기 관계와 관측/추론 구분으로 정리했습니다. 자료 작성과 기능 확인은 사용자 이해 완료를 뜻하지 않습니다. 다음 학습은 아직 미충족인 CPU 증거와 미션 전체 목표의 설명 누락을 PM과 확인하는 것이며, 이번에 추가 앱 실행은 하지 않았습니다.

## TASK-006: 공통 관측과 실행 후 안전 정리

### 이전 단계와 이번 목표

TASK-001의 실행 조건·PID·CSV와 TASK-002의 MemoryGuard 비교, TASK-004의 스레드 대기 증거를 이제 같은 입력 형식으로 수집합니다. [미션 원문 §2·§4](harness/MISSION.md)의 메모리 증가·대상 프로세스 CPU 급상승·PID 생존과 스레드 정체는 서로 다른 증거가 필요하지만, 사용자가 실행 전에 장애 종류를 맞힐 필요는 없습니다. [REQ-002~004](harness/REQUIREMENTS.md)와 [TASK-006](harness/tasks/TASK-006.md)에 맞춰 세 환경값만 바꾸는 공통 명령, 실행별 원본 보존, 관측 후 이번 실행 앱의 안전한 정리를 구현했습니다. 수집 성공이 세 장애의 입증이나 [REQ-003](harness/REQUIREMENTS.md)의 완료를 뜻하지는 않습니다.

먼저 **launcher와 작업 자식**을 구분하세요. 준비 도구가 띄운 첫 PID는 launcher이고, 그 아래에서 RSS가 증가하는 자식이 관제 대상 `app_pid`입니다. `monitor.csv`의 `%CPU`는 `ps`가 계산한 **시작 이후 수명 평균**, `cpu-samples.csv`의 `%CPU`는 `top`의 **구간 표본**입니다. 앱 로그의 `CpuWorker Current Load`는 앱 내부 값이므로 두 OS 수치로 환산할 수 없습니다. `RUNNING`은 PID가 작업 가능한 상태라는 표지이지 응답·진행을 검증한 값이 아닙니다. 현재 코드는 [MISSION의 Linux 일반 사용자·고정 포트·표준 도구 제약](harness/MISSION.md)을 따르며 바이너리 내부를 분석하지 않습니다.

### 입력부터 저장·정리까지 코드 읽기

#### 1. 설정 세 개로 시작하고 기존 관제 호출은 구분한다

현재 권장 명령의 한 예는 `bash ./monitor.sh 400 40 true 60`입니다. [인자 분기와 시간 검사](../monitor.sh#L63)는 3/4인자를 새 관측으로, `PID NEW_LOG_FILE` 두 인자를 기존 CSV 단독 관제로 보냅니다. `60`을 생략하면 기본 60초이며 허용 범위는 15~300초입니다. 2인자 경로는 [같은 `sample_csv` 함수](../monitor.sh#L7)를 직접 호출하고 앱을 정리하지 않습니다. `run-memory-comparison.sh`와 사용자 `memory-test.sh`가 그 호출 형식을 사용하지만, **최종 TASK-006 코드의 2인자 경로를 다시 실행한 확인은 없습니다.** 이전 `observe.sh`와 세 장애별 파일은 [호환 진입점](../observe.sh#L8)이며 실제 공통 관측 구현은 `monitor.sh`에 있습니다.

#### 2. 준비 함수가 원본 위치와 이번 실행 PID를 정한다

[설정값 호출부](../monitor.sh#L224)는 [준비 함수](../prepare-env.sh#L9)를 `source`하므로 `run_dir`, `launcher_pid`, `app_pid`가 **같은 셸**에 남습니다. 준비 함수는 Linux·일반 사용자·아키텍처·포트 15034와 값 범위([준비 조건](../prepare-env.sh#L35), [설정 검사](../prepare-env.sh#L75))를 확인합니다. 실행별 고유 디렉터리를 만든 뒤 `AGENT_LOG_DIR` 등을 export하고, 바이너리의 표준출력·오류를 `app.log`에 이어 씁니다([로그·앱 시작](../prepare-env.sh#L123)). 앱이 직접 쓰는 `agent_app.log`는 앱 쪽 산출물이므로 부트 실패 때 없을 수 있습니다. 준비 함수는 launcher `$!`의 자식을 확인해 `app_pid`를 정하며([자식 선택](../prepare-env.sh#L145)), 이 시점의 `Started (boot unverified)`는 부트 성공 표시가 아닙니다.

[시작 tick 읽기](../monitor.sh#L94)는 Linux `/proc/PID/stat`의 필드 22를 읽어 두 PID와 함께 보관합니다([준비 직후 저장](../monitor.sh#L231)). PID 숫자는 나중에 다른 프로세스에 재사용될 수 있으므로 종료 신호의 대상을 구분하는 값입니다. 시작값을 얻지 못하면 이번 실행임을 증명할 수 없어 자동 신호를 보내지 않고 실패를 알립니다.

#### 3. 파일마다 출처와 측정 뜻을 구분한다

[새 파일 열기](../monitor.sh#L238)는 `set -C`로 기존 내용을 덮어쓰지 않고, 파일 디스크립터 3·4·6을 각각 `observation.txt`·`cpu-samples.csv`·`thread-observation.txt`에 연결합니다. 디스크립터는 `>&3`처럼 쓰는 출력 통로이며, 실패하면 정상 수집으로 표시하지 않습니다. 앱 원문 `app.log`·`agent_app.log`와 별개로, [백그라운드 CSV 수집 시작](../monitor.sh#L259)은 `sample_csv app_pid monitor.csv &`를 실행하고 `$!`를 **앱 PID가 아닌 관제 수집기 PID**로 저장합니다.

`sample_csv`는 [헤더·noclobber](../monitor.sh#L17) 후 `ps`의 수명 평균 CPU·RSS(KiB)·시스템 대비 메모리 비율·상태를 약 1초마다 씁니다([반복 수집](../monitor.sh#L27)). Z/X 또는 PID 소멸은 `EXITED`이고, 표본 읽기 오류를 임의의 0으로 기록하지 않습니다. 자식 PID의 RSS 변화는 메모리 증가의 OS 근거입니다. `monitor.csv`의 `%MEM`은 앱 `MEMORY_LIMIT` 소진율이 아닙니다.

[메인 관측 루프](../monitor.sh#L264)는 Bash `SECONDS`로 관측 한도를 확인합니다. 앱 PID의 시작값을 재확인하고, 약 15초마다 [앱 PID 한정 `ps -L`](../monitor.sh#L133)을 저장합니다. `ps -L`의 TID·상태·`wchan`은 스레드 정체를 관찰하는 자료이며 `futex_wait`만으로 락 소유자를 알 수 없습니다. CPU는 [두 대상 PID의 `top -n 2`](../monitor.sh#L278)를 호출해 첫 프레임을 버리고 두 번째 프레임만 [구간 CSV 처리](../monitor.sh#L163)에 전달합니다. 시작값이 맞으면 `identity_status=confirmed`, 표본 뒤 PID가 사라져 재확인할 수 없으면 `unconfirmed_after_exit`로 보존하고 **앱 CPU를 단독 입증한 값으로 쓰지 않습니다**. 새 시작값이 다르면 재사용 PID의 행을 앱 표본으로 저장하지 않습니다. `ppid_at_launch`는 실행 시작 때 확인한 앱→launcher 관계이지 매 표본 시각의 새 조회가 아닙니다.

#### 4. 관측 종료 당시 상태와 장애 신호를 먼저 남긴다

[종료 시점 검사와 관제 회수](../monitor.sh#L296)는 앱이 이미 사라졌으면 CSV의 `EXITED` 행을 기다리고, 시간 한도에 살아 있으면 **관제 수집기**에 TERM을 보냅니다. `wait`는 그 백그라운드 수집기의 실제 종료값을 받습니다. 이 경우 관제 status 143은 수집기를 종료한 결과이며 앱의 Watchdog·자연 종료 신호가 아닙니다. 반대로 CSV `EXITED`와 정리 전 `absent`는 앱 작업이 도구 정리 전에 끝났다는 근거지만 원인은 앱 로그와 함께 읽어야 합니다. 부트 표식·CSV 행·대상 CPU 행이 없으면 수집 실패로 남깁니다([검사](../monitor.sh#L324)).

[요약 작성](../monitor.sh#L330)은 **자동 정리 전에** PID 상태와 마지막 관제·CPU·스레드 표본을 기록합니다. [로그 신호 함수](../monitor.sh#L146)는 MemoryGuard 한도/자체 종료, `CpuWorker` 임계치, Watchdog 언급, 스레드 WAITING/BLOCKED를 각각 한 줄로 표시합니다. `grep` 종료값 1은 해당 문구 없음이고, 2 이상은 로그 읽기 실패라 요약에 오류를 쓰고 전체 결과도 비정상으로 만듭니다. 이 다섯 표시는 장애명 판정이 아닙니다. 앱 내부 임계치 위반은 OS CPU 급상승이나 Watchdog SIGTERM을 증명하지 않으며, WAITING/BLOCKED는 반복 OS·로그 정체와 맞춰야 합니다.

#### 5. 이번 실행 두 PID만 정리하고 포트 상태를 확인한다

[요약 뒤 자동 호출](../monitor.sh#L361)은 기록한 launcher·앱 PID와 각 시작 tick을 [정리 도구의 4인자 경로](../kill-agent-leak.sh#L87)에 넘깁니다. 정리 도구의 [`identity`](../kill-agent-leak.sh#L18)는 매 신호 전에 UID·시작값을 다시 비교합니다. 처음 고른 목록을 다시 검색해 다른 실행 PID를 추가하지 않고, 동일한 살아 있는 대상에만 TERM 후 필요할 때 KILL을 보냅니다([신호와 재확인](../kill-agent-leak.sh#L103)). `ss`가 실패하면 포트 해제로 간주하지 않고, LISTEN이 남아도 그 점유자를 새 종료 대상으로 삼지 않습니다([포트 확인](../kill-agent-leak.sh#L149)). 요약의 최종 상태는 [시작 tick을 다시 비교](../monitor.sh#L116)해 재사용 PID를 이번 앱으로 표시하지 않습니다. **정리 뒤 absent는 관측 중 앱 자연 종료의 증거가 아닙니다.**

인자 없는 [수동 정리 경로](../kill-agent-leak.sh#L39)는 현재 UID와 저장소 바이너리의 정확한 실행 경로가 일치하는 후보를 보여 준 뒤 대화형 확인을 받습니다. 이는 다른 실행도 후보가 될 수 있는 별도 기능이며, TASK-006의 네 사용자 실행에서는 **자동 4인자 정리만** 확인됐습니다. 수동 무인자·신호 경합·`ss` 오류의 실제 실행은 미검증입니다.

### 파일·프로세스 안전성과 아직 실행하지 않은 경로

고유 실행 디렉터리와 `set -C`는 예전 증거의 덮어쓰기를 막습니다([준비 디렉터리](../prepare-env.sh#L123), [관제 파일](../monitor.sh#L17), [공통 파일](../monitor.sh#L246)). 관측·부트·파일 저장 또는 앱 로그 읽기가 실패하면 부분 파일을 성공 증거로 꾸미지 않고 비정상 상태로 끝내되, 이번 실행 시작값을 확인했으면 정리를 시도합니다. 준비 도중 시작값을 얻지 못하면 다른 PID에 잘못 신호를 보내지 않도록 자동 종료를 생략합니다([초기 실패 경로](../monitor.sh#L227)). PID 조회와 신호 사이의 짧은 재사용 경합은 셸 도구만으로 원자적으로 제거할 수 없으며, 신호 직전 재검증으로 범위를 좁힙니다. 실제 secret은 기록하지 않고 준비 도구의 공개 시험용 키만 확인합니다.

네 사용자 실행으로 확인한 것은 **새 3/4인자 공통 경로의 관측 중 자식 종료 두 경우와 시간 만료 뒤 정리 두 경우**입니다. 기존 2인자 호출의 재실행, 일부 파일·로그·도구 실패, INT/TERM 중단, 수동 무인자 정리의 실제 실행은 하지 않았습니다. 구현과 [독립 리뷰·수정 재검토](harness/reviews/REVIEW-TASK-006-FIX.md)의 정적 확인을 이 미검증 경로의 실행 성공으로 바꾸어 쓰지 않습니다. TASK-001·004 절의 옛 코드 행 링크와 현재 wrapper 구조의 차이는 이 절에서 현재 흐름을 우선해 읽고, 이전 절 자체의 정리는 별도 PM 확인이 필요합니다.

### 동료평가에서 스스로 설명해 보기

아래 질문을 먼저 답한 뒤 근거를 확인하세요. 실제 평가 문제라는 뜻은 아닙니다.

1. 같은 `monitor.sh`에 세 설정값을 주는 호출과 `PID CSV경로` 두 인자 호출은 무엇이 다르고, 앱은 언제 정리되나요?
2. `CpuWorker Current Load`가 51.89%이고 앱이 종료됐는데 왜 CPU 과점유·Watchdog 종료가 아직 미입증인가요?
3. 400/40/true의 PID가 `RUNNING`인데 왜 교착을 추론하며, `futex_wait` 하나로 결론을 내릴 수 있나요?
4. 관제 status 143과 cleanup status 0, 정리 전 `SNl+`를 함께 보면 앱 생존·종료 시점을 어떻게 설명하나요?
5. `top` 표본 직후 PID가 사라지거나 재사용되면 CSV 행과 종료 신호는 어떻게 달라지나요?
6. `agent_app.log`가 존재하지만 읽기 실패하면 ‘문구 없음’으로 써도 되나요? 포트에 다른 프로세스가 남으면 정리 도구는 어떻게 하나요?

답변 근거:

- 1: [입력 분기](../monitor.sh#L63)의 2인자는 `sample_csv`만 실행하고 앱을 남깁니다. [3/4인자 흐름](../monitor.sh#L72)은 준비·세 표본·요약 뒤 [자동 정리](../monitor.sh#L361)까지 수행합니다.
- 2: [CPU 요약 신호](../monitor.sh#L337)는 내부 임계치를 OS CPU와 구별합니다. [512/80 실행 기록](harness/tasks/TASK-006.md#cpu-설정-공통-관측-사용자-실행-51280false-60초-한도)의 확인된 `top` 최대 4.0%와 Watchdog·SIGTERM 문구 부재를 연결해야 합니다.
- 3: [CSV RUNNING 정의](../monitor.sh#L32)는 응답 검사가 아닙니다. [교착 실행 기록](harness/tasks/TASK-006.md#교착-설정-공통-관측-사용자-실행-40040true-60초-한도)의 A/B 순환 로그, 반복 RSS·CPU·스레드 정체를 함께 보세요.
- 4: [관제 회수](../monitor.sh#L304)의 143은 수집기 TERM이고, [정리 전 요약](../monitor.sh#L330) 뒤 [앱 정리](../monitor.sh#L361)를 실행합니다. 60초 생존 하한 이후 앱이 자연 종료했다고 말할 근거는 없습니다.
- 5: [CPU 동일성 분기](../monitor.sh#L199)는 사라진 PID의 행을 `unconfirmed_after_exit`로 보존하되 단독 증거로 확정하지 않고, 시작 tick이 바뀌면 이번 앱 행으로 쓰지 않습니다. [종료 신호 확인](../kill-agent-leak.sh#L18)은 UID·시작값이 맞는 대상만 허용합니다.
- 6: [로그 검색 분기](../monitor.sh#L146)는 `grep` 오류를 요약·비정상 반환으로 전달합니다. [포트 확인](../kill-agent-leak.sh#L149)은 LISTEN을 보고하지만 새 점유자를 종료 대상에 추가하지 않습니다.
